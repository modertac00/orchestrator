Executive Summary

6repositories analyzed
2frontends
2NestJS APIs
2shared packages
1verified reporting endpoint
1critical DI wiring gap

Current architecture

  • The main platform is a React SPA backed by a broad NestJS/PostgreSQL API with Supabase authentication and project-level authorization.
  • Reporting is a separate React SPA and NestJS service. Its only verified data route is Scope 1 stationary combustion breakdown.
  • The reporting service reads ESM tables directly and invokes @moderta/reporting-core in-process.
  • Mint Design System is consumed by the reporting frontend, not the main frontend.

Operational reality

  • The full organization report currently defaults to a frontend fixture.
  • The reporting API module graph does not provide a required repository token, blocking the sole route’s service construction.
  • PDF, metadata DB and S3 JSON artifact code exists but is not connected to the active module/controller flow.
  • No main ESM route/client connects users into reporting.
Highest-priority findingScope1StationaryBreakdownService injects REPORT_GENERATION_REPOSITORY, but ReportingMetadataModule is never imported by ReportingModule or AppModule. The reporting API should be treated as non-operational until the module graph is fixed and startup-tested.

Overall System Architecture

07

ESM Main Platform

Main frontend

  • React Router creates one root app shell and lazy dashboard/product/auth pages.
  • RTK Query uses VITE_API_END_POINT, adds bearer token from the accessToken cookie and attempts refresh.
  • Project context is embedded in routes and API paths.
  • No reporting route, link or reporting API base URL was found.

Main API

  • Nest bootstrap enables configurable CORS, global validation and Swagger.
  • AppModule imports 30+ feature modules and configures Sequelize PostgreSQL.
  • SupabaseAuthGuard establishes identity; ProjectAccessGuard verifies userId + projectId.
  • S3 uploads support direct files and presigned PUT URLs.
08

ESM Reporting Platform

Verified stationary data repository and core calculation Partial API runtime and full-report integration Planned metadata/S3/PDF paths
  1. Full organization report setup uses a mock fixture unless VITE_REPORT_DATA_SOURCE=api.
  2. The real get/generate/download paths are environment driven and blank in the supplied configuration.
  3. The only concrete backend route is GET /reports/scope-1/stationary-breakdown.
  4. The service reads stationary rows directly, converts gas breakdown kilograms to tonnes, and calls the core calculator.
  5. The service then attempts to record a completed generation through an unresolved provider.

Data Architecture

Operational data

The main API owns PostgreSQL models across ESM domains. The reporting service duplicates a narrow read model for two stationary tables and joins the calculation relation.

Reporting metadata

report_generations and report_artifacts models and a separate connection provider exist, but the module is not part of the active application graph.

Replica statusNo code establishes primary/replica topology, read preference, lag handling or a replica-specific endpoint. A generic reporting DB_* target could be configured to a replica operationally, but that would be outside supplied evidence.
13

Authentication and Organization Context

Main platform enforcement

The API guard extracts projectId from route parameters or request body and calls AuthorizationService.verifyProjectAccess(user.userId, projectId).

Reporting enforcement gap

The reporting frontend sends its access-token cookie as a bearer token, but the reporting controller accepts only a project UUID and attaches no authentication or authorization guard.
